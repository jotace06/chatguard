# ChatGuard

> 라이브 채팅과 AI 콘텐츠 모더레이션을 결합한 실시간 서비스.
> Kubernetes 위에 구축하고, **트래픽 폭주와 장애 상황에서의 동작을 실측으로 검증**했습니다.

---

## 어떤 서비스인가

라이브 스트리밍 채팅은 방송의 재미를 키우는 공간이지만, 동시에 악성 채팅이 끊이지 않는 곳이기도 합니다. 명백한 비속어는 키워드로 걸러낼 수 있지만 자모를 분리하거나 기호를 끼워 넣어 우회하는 채팅, 맥락 속에서 공격하는 채팅은 잡기 어렵습니다. **실시간성을 해치지 않으면서 이런 채팅을 어떻게 걸러낼 것인가**에서 출발한 프로젝트입니다.

영상 송출은 범위에서 제외하고 채팅에 집중했습니다. 들어오는 모든 채팅을 두 단계로 검열해, 명백한 금칙어는 전파 전에 차단하고 맥락상 유해한 메시지는 AI가 판정해 가립니다. AI가 놓치는 표현은 운영자가 금칙어를 실시간으로 추가하거나 방 전체 채팅을 일시 정지해 메웁니다.

<img src="docs/demo-chat.gif" width="400" alt="AI 검열이 적용된 실시간 채팅">

_트래픽이 몰리는 구간. 통과한 메시지는 그대로 노출되고, AI가 유해로 판정한 메시지는 가려진 채 표시된다._

### 검열은 두 단계로

|        | 1단계 · 키워드                           | 2단계 · AI                  |
| ------ | ---------------------------------------- | --------------------------- |
| 언제   | 노출 **전**에 동기 검사                  | 노출 **후**에 비동기 판정   |
| 무엇을 | 비속어·혐오 표현, 자모 분리 등 우회 표현 | 맥락으로 판단해야 하는 표현 |
| 결과   | 즉시 차단, 발신자에게만 오류             | 사후 블러                   |

실시간성을 지키기 위해 **먼저 보여주고, 위험하면 가린다**를 택했습니다. 전송이 AI 판정을 기다리지 않으므로, 응답 시간이 모델 추론 시간에 묶이지 않습니다.

| 측정 구간                                     | 실측 p95                    |
| --------------------------------------------- | --------------------------- |
| 전송 — 메시지를 보내고 화면에 뜨기까지        | **40ms**                    |
| 검열 반영 — 큐에 들어가고 블러가 전파되기까지 | **1초 미만** (워커 확장 후) |

전송이 판정을 기다렸다면 앞의 숫자가 뒤의 숫자보다 작을 수 없습니다.

### AI가 놓치는 것은 운영자가 메운다

기획 단계에서는 AI가 맥락 속 비난이나 돌려 말하는 표현도 상당 부분 잡아줄 것으로 기대했습니다. 그런데 실시간 처리와 빠른 확장을 위해 고른 작은 CPU 모델(한국어 혐오 표현 분류 모델 UnSmile)은 그런 표현을 기대만큼 잡지 못했습니다. 더 큰 모델이나 여러 단계의 판정으로 정확도를 끌어올리는 방법도 있었지만, 5주라는 기간과 이 프로젝트의 초점(실시간 처리와 확장)을 고려하면 별개의 과제라고 판단했습니다.

그래서 모델이 완벽하지 않다는 것을 전제로 두고, 그 빈틈을 사람이 바로 메울 수 있는 운영 도구를 만들었습니다.

- **금칙어 실시간 추가** — AI가 놓친 표현을 운영자가 금칙어로 등록하면, 다음 메시지부터는 1단계에서 전파 전에 차단됩니다. 특정 상황에서 갑자기 생겨난 비하 표현처럼 모델이 배운 적 없는 말에 특히 유효합니다.
- **채팅 일시 정지** — 유해 채팅이 한꺼번에 쏟아져 하나씩 대응할 수 없을 때 방 전체를 멈춥니다.

## 배포 구조

3개 가용영역에 걸친 VPC 안에서, 서브넷을 노출 수준에 따라 세 층으로 나눴습니다. 외부에서 닿을 수 있는 것은 퍼블릭 서브넷의 ALB 하나뿐이고, 애플리케이션 파드는 프라이빗 서브넷에, 데이터베이스와 Redis는 **인터넷으로 나가는 라우트가 아예 없는** 격리 서브넷에 둡니다.

![ChatGuard prod 아키텍처](docs/architecture-prod.svg)

- **외부에서 들어오는 요청은 ALB가 경로로 나눕니다.** `/`는 정적 파일을 서빙하는 nginx 파드로, `/api`와 `/ws`는 Chat Server로 **직접** 보냅니다. nginx가 백엔드 요청까지 받아 넘기는 구성이 더 흔하지만, 그러면 ALB에게 보이는 대상이 nginx 하나뿐이라 Chat Server가 몇 개로 늘었는지 알 수 없습니다. 새 연결을 한산한 파드로 보내는 일도, 종료될 파드의 연결을 미리 빼는 일도 ALB가 개별 파드를 알아야 가능합니다. 한번 맺으면 오래 유지되는 WebSocket에서는 연결되는 순간의 분산이 사실상 유일한 기회입니다.
- **데이터 계층은 인터넷과 끊어져 있습니다.** RDS와 Redis가 있는 격리 서브넷에는 NAT도 인터넷 게이트웨이도 연결돼 있지 않습니다. 애플리케이션 파드가 있는 프라이빗 서브넷은 이미지를 받아야 해서 NAT로 나가지만, 데이터 계층은 나갈 일이 없으므로 경로 자체를 만들지 않았습니다.

<details>
<summary><b>dev / prod 환경 차이</b></summary>

<br>

두 환경은 같은 Terraform 모듈을 쓰고 변수만 다릅니다. 환경을 브랜치로 나누지 않고 디렉터리와 변수로 분리했기 때문에, 한쪽에만 적용된 수정이 생기지 않습니다.

dev는 매일 만들고 지우는 환경이라 **비용과 생성 속도**를 우선했습니다. AZ 하나에 NAT 한 대, 단일 AZ DB, 복제본 없는 Redis입니다. prod는 **구조적으로 HA를 갖추되 인스턴스 크기는 최소**로 잡았습니다. 장애 주입 실험에서 "Redis나 노드가 죽어도 살아남는가"를 확인하려면 다중화가 실제로 돼 있어야 하는데, 그건 구성의 문제지 인스턴스 사양의 문제가 아니기 때문입니다.

|             | dev                              | prod                                                          |
| ----------- | -------------------------------- | ------------------------------------------------------------- |
| AZ / NAT    | 2 AZ · NAT 1대                   | 3 AZ · AZ마다 NAT                                             |
| EKS 노드    | t4g.medium × 2                   | m7g.large × 5                                                 |
| Chat Server | min 1 / max 5                    | min 3 / max 5                                                 |
| Worker      | min 1 / max 5                    | min 2 / max 10                                                |
| RDS         | db.t4g.micro, 단일 AZ, 백업 없음 | db.t4g.small, Multi-AZ, 백업 7일                              |
| Redis       | cache.t4g.micro 1노드            | cache.t4g.small 2노드, 자동 failover                          |
| 배포        | main 머지 시 자동                | 승인 게이트 통과 후, dev에서 검증된 이미지를 재빌드 없이 승격 |

</details>

## 핵심 동작

메시지 한 건은 두 갈래로 끝날 수 있습니다. 명백한 금칙어는 전파되기 전에 끝나고, 통과한 메시지는 일단 노출된 뒤 AI 판정 결과에 따라 사후에 가려질 수 있습니다.

![메시지 한 건의 처리 여정](docs/message-journey.svg)

이 흐름을 만들면서 풀어야 했던 문제가 세 가지였습니다.

### 흩어진 파드에 어떻게 동시에 전달하나

WebSocket은 한 번 맺으면 끊을 때까지 유지되는 연결입니다. 사용자 A가 접속하면 그 연결은 **A를 받아준 파드 하나의 메모리 안에** 객체로 남습니다. A에게 무언가를 보내려면 그 객체를 가진 파드가 직접 써야 합니다. 다른 파드는 A가 존재한다는 사실조차 모릅니다.

서버가 한 대일 때는 문제가 없습니다. 모든 연결이 그 한 대 안에 있으니 목록을 순회하며 쓰면 끝입니다. 그런데 파드를 여러 개로 늘리면 같은 방 사람들이 서로 다른 파드에 흩어집니다. A의 메시지를 받은 파드 1은 파드 2에 붙어 있는 B와 C에게 전달할 방법이 없습니다.

![파드 간 메시지 전파](docs/message-fanout.svg)

**파드끼리 직접 연락하는 방법은 택하지 않았습니다.** 파드 1이 파드 2에게 "이 메시지 좀 전해줘"라고 하려면 지금 살아 있는 파드가 몇 개이고 각각 어디 있는지 알아야 합니다. 오토스케일로 파드가 수시로 생기고 사라지는 환경에서 그 목록을 정확히 유지하는 것 자체가 또 하나의 문제입니다.

**대신 Redis를 중계소로 두고, 모든 파드가 그곳을 바라보게 했습니다.** 메시지를 받은 파드는 Redis에 던져 넣기만 합니다. 누가 듣고 있는지 알 필요가 없습니다. Redis는 그것을 듣고 있던 모든 파드에게 복사해 보내고, 각 파드는 자기 메모리에 있는 WebSocket 연결로 내보냅니다. 이 방식이 **pub/sub**이고, 던져 넣는 주소를 **채널**이라고 부릅니다.

- **채널은 만드는 것이 아니라 이름만 맞추면 됩니다.** 보내는 쪽이 `room:1`이라는 이름으로 던지고 받는 쪽이 같은 이름을 듣고 있으면 성립합니다. 방이 새로 생겨도 Redis에 등록할 것이 없습니다.
- **채널 이름에 방 번호를 넣어 구분합니다.** 이름이 하나뿐이면 1번 방 메시지가 2번 방 사람에게도 갑니다. 1번 방 메시지는 `room:1`로만 나갑니다.
- **받는 쪽은 `room:*` 하나로 전부 듣고, 받은 뒤에 거릅니다.** 방마다 구독을 붙였다 떼는 대신, 모든 파드가 모든 방의 메시지를 받아 자기한테 그 방 사용자가 있을 때만 전달하는 방식입니다. 구독 관리 코드가 없어 단순하고 방이 수십 개인 지금은 버려지는 양이 무의미하지만, 수천 개가 되면 모든 파드가 모든 트래픽을 받게 되므로 그때는 방별 구독으로 바꿔야 합니다.
- **발신자도 Redis를 거쳐 자기 메시지를 돌려받습니다.** 파드 1이 A에게 곧바로 밀어주는 편이 한 단계 빠르지만, 그러면 전달 경로가 둘이 되어 같은 메시지가 두 번 보일 수 있습니다. 모든 전달을 한 경로로 통일했습니다.
- **던진 메시지는 남지 않습니다.** 그 순간 듣고 있던 파드에만 복사되고 사라집니다. 그래서 전파와 저장이 짝을 이룹니다. 지금 보고 있는 사람은 Redis에서 받고, 나중에 들어온 사람은 DB에서 읽습니다.

**메시지 브로커를 따로 두지 않은 이유.** 여러 수신자에게 동시에 뿌리는 문제는 Kafka나 RabbitMQ 같은 전용 브로커, AWS라면 SNS·SQS 조합으로도 풀 수 있습니다. 이들은 메시지를 보관해 두었다가 못 받은 쪽에 다시 주는 보장이 강한 대신, 구성 요소가 하나 더 늘고 파드마다 자기 큐나 컨슈머 그룹을 들고 있어야 합니다. 파드가 수시로 생기고 사라지는 환경에서는 그 관리가 또 일이 됩니다.

Redis pub/sub은 반대로 **보낸 순간 듣고 있지 않았으면 그만**입니다. 보장이 약한 대신 가볍습니다. 이 서비스에서는 이 약점이 치명적이지 않았습니다. 메시지의 원본은 DB에 있고, 연결이 끊겼던 사용자는 재접속하면서 히스토리를 다시 받아 화면을 맞추기 때문입니다. 실시간 전파는 "지금 보고 있는 사람에게 빠르게"만 하면 되고, 정확성은 DB가 책임집니다.

결정적으로 **Redis는 이미 필요했습니다.** AI 검열 대기열과 참여자 목록을 둘 곳이 있어야 했으니까요. 위 그림에서 파드 1이 Redis로 보내는 화살표가 둘인데, 하나는 방금의 채널이고 다른 하나는 검열 대기열입니다. 채널은 듣고 있는 **모두에게 복사**되고, 대기열은 **한 작업을 한 워커만** 가져갑니다. 성질이 정반대인 두 문제를 같은 저장소의 다른 자료구조로 풀었기 때문에, 전파를 위해 인프라를 추가하지 않았습니다.

### 느린 AI 검열이 채팅을 막지 않으려면

두 가지 요구가 맞섭니다. 채팅은 즉시 떠야 하는데, AI 판정은 모델이 문장을 읽는 동안 수백 밀리초가 걸립니다. 모든 메시지를 판정한 뒤에 보여주면 전송 지연이 모델 추론 시간에 그대로 묶입니다. 그래서 검열을 성격에 따라 둘로 쪼갰습니다.

|            | 언제 검사   | 기다리나           | 무엇을 잡나                  |
| ---------- | ----------- | ------------------ | ---------------------------- |
| 1차 키워드 | 노출 **전** | 기다림 (즉시 끝남) | 명백한 금칙어와 그 우회 표현 |
| 2차 AI     | 노출 **후** | 기다리지 않음      | 문맥으로 판단해야 하는 표현  |

**1차는 단순 문자열 비교가 아닙니다.** 금칙어 사이에 숫자나 기호를 끼워 넣거나 자모를 분해해 적는 우회가 흔합니다. 그래서 한글 메시지는 한글이 아닌 문자를 걷어내고, 분리된 자모를 완성형 글자로 다시 조합한 뒤에 대조합니다. 금칙어 목록은 각 파드가 메모리에 들고 있어서 메시지마다 DB를 조회하지 않고, 관리자가 목록을 바꾸면 신호를 받아 다시 읽습니다.

**둘 사이를 잇는 것이 큐입니다.** Chat Server는 워커에게 직접 요청하지 않고 Redis의 목록에 일감을 넣은 뒤 곧장 다음 메시지를 처리하러 갑니다. 워커는 그 줄에서 하나씩 꺼내 처리합니다. 이렇게 두면 두 가지를 얻습니다. 워커가 느려져도 채팅 전송은 영향을 받지 않고, 폭주가 와도 일감이 사라지지 않고 줄에 쌓여 차례를 기다립니다. 그리고 쌓인 길이가 곧 "얼마나 밀렸는가"라서, 이 값을 [오토스케일의 신호](#무엇을-보고-얼마나-늘리는가)로 그대로 씁니다.

**적재와 전파의 순서를 고정했습니다.** 1차 검열을 통과한 메시지는 ① DB에 저장하고 ② 검열 큐에 넣은 뒤 ③ 전파합니다. 큐에 넣는 데 실패하면 전파하지 않고 발신자에게 오류를 돌려줍니다.

순서가 중요한 이유는 실패했을 때 남는 상태가 달라지기 때문입니다. 전파를 먼저 하고 큐에 넣다가 실패하면, 그 메시지는 **모두의 화면에 떠 있는데 AI 검열은 영원히 받지 않는 상태**가 됩니다. 검열 서비스에서 가장 나쁜 결과입니다. 순서를 바꾸면 같은 실패가 "아무에게도 안 보였고 다시 보내면 됨"으로 바뀝니다. 코드에서 두 줄의 순서를 바꾸는 것이 전부였습니다.

저장과 큐 적재는 하나의 DB 트랜잭션 안에서 일어납니다. 큐 적재가 실패하면 예외가 트랜잭션을 되돌리므로, 그 메시지는 DB에도 남지 않습니다. 남는 실패는 반대 방향 하나입니다. 큐 적재까지 성공한 뒤 DB 커밋이 실패하면 큐에는 DB에 없는 메시지의 검열 작업이 남는데, 워커가 처리해도 갱신할 대상이 없을 뿐 화면에 드러나는 것은 없습니다. 실패가 생기더라도 무해한 쪽으로만 남는 구조입니다. 다만 이 경로는 코드로 확인한 것이고, Redis 장애를 주입해 실측하지는 않았습니다.

### 이미 노출된 메시지를 어떻게 가리나

워커가 "이 메시지는 유해하다"고 판정했을 때, 그 메시지는 이미 여러 파드에 흩어진 여러 화면에 떠 있습니다. 앞의 전파 문제와 같은 모양이라 해법도 같습니다.

- **같은 채널을 그대로 씁니다.** 채팅 메시지가 지나가던 그 방 채널에 "이 메시지를 가려라"라는 신호를 흘려보냅니다. 구독 중인 모든 파드가 받아 각자의 클라이언트에 전달하고, 브라우저가 해당 메시지를 찾아 블러 처리합니다. 전파 장치를 새로 만들 필요가 없었습니다.
- **어느 메시지인지는 ID로 지목합니다.** Chat Server는 메시지를 받자마자 고유 ID를 발급해 저장·큐·전파에 모두 같은 값을 씁니다. 그래서 판정이 끝난 시점에 "그 ID의 메시지"라고만 말하면 됩니다.
- **DB를 먼저 바꾸고 신호를 보냅니다.** 신호는 그 순간 접속해 있는 사람만 받습니다. 잠깐 끊겼던 사람은 재접속하면서 히스토리를 다시 받는데, 그때 DB가 이미 갱신돼 있어야 놓친 블러가 복원됩니다. 순서가 반대라면 그 틈에 들어온 사람에게는 유해 메시지가 그대로 보입니다.
- **화면은 DB의 상태값 하나만 보고 그립니다.** 프론트엔드가 "가려야 할 메시지 목록"을 따로 들고 있지 않습니다. 실시간 신호로 받든 히스토리로 받든 같은 값을 보기 때문에 두 경로가 어긋나지 않습니다.

## 무엇을 보고 얼마나 늘리는가

두 컴포넌트는 포화되는 이유가 다릅니다. Chat Server는 연결을 붙들고 있느라 메모리가 차고, 워커는 추론하느라 CPU가 찹니다. 그래서 CPU 사용률 같은 공통 지표 대신, 각자가 실제로 포화되는 원인을 신호로 삼았습니다.

![오토스케일의 두 축](docs/autoscale-axes.svg)

- **접속 축** — Prometheus에 쌓인 WebSocket 접속 수 합계를 KEDA가 직접 조회해, 파드 하나가 100 연결을 맡는 기준으로 레플리카를 정합니다. 접속이 320명이면 4개가 됩니다. 여기에 파드당 200 연결이라는 하드 상한이 별도로 걸려 있어, 스케일이 못 따라가도 한 파드가 메모리로 무너지지는 않습니다.
- **처리량 축** — 앞서 본 검열 큐의 길이를 보고 워커를 늘립니다. 파드 하나가 대기열 5건을 맡는다고 보고 `큐 길이 ÷ 5`만큼 띄우므로, 50건이 쌓이면 10개가 됩니다. 큐 깊이는 밀린 일감을 그대로 나타내는 값이라 지연이 커지기 전에 신호가 먼저 움직입니다.
- **확장은 빠르게, 축소는 느리게.** 양쪽 모두 늘릴 때는 대기 없이 즉시 올립니다. 줄일 때는 Chat Server가 10분, 워커가 3분 동안 지켜본 뒤 내려가기 시작하고, 그 뒤에도 한 번에 하나씩만 줄입니다. Chat Server는 파드가 사라질 때마다 그 파드에 붙어 있던 연결이 한꺼번에 재접속을 시도하고, 워커는 모델을 프로세스 안에 올리기 때문에 새 파드의 콜드스타트 비용이 큽니다.
- **상한에 닿으면 더 늘지 않습니다.** 워커는 10개, Chat Server는 5개가 끝입니다. 그 위로는 큐가 쌓이거나 새 연결이 거절되는데, 두 상황 모두 부하 테스트에서 실제로 관측했습니다.

두 축을 분리했기 때문에 부하 테스트도 접속 수와 메시지 처리량을 따로 밀어서 진행했습니다. 한 번에 둘 다 극한으로 밀면 어느 쪽이 병목인지 구분되지 않습니다.

## 부하·장애 테스트

확인하려던 것은 두 가지였습니다. 부하가 몰릴 때 시스템이 설계대로 늘어나는가, 그리고 장애가 났을 때 버티는가. 목표는 "몇 명까지 버티는가"라는 절대 수치가 아니라, 오토스케일이 설계대로 반응하는지와 한계에 닿았을 때 무엇이 먼저 막히는지를 보는 것이었습니다.

처리량 축과 접속 축은 테스트를 따로 진행했고, 한 실험에서는 조건(워커 상한, 노드 수, 부하량 등) 하나만 바꿨습니다. 측정해서 병목을 찾고, 조정한 뒤, 같은 부하로 다시 재는 방식입니다. 조정이 예상대로 먹히지 않으면 원인을 다시 찾고 다시 쟀기 때문에, 질문 하나에 실험이 여러 번 필요했습니다. 모든 실험은 prod 환경에서 진행했습니다.

### 병목은 파드 수가 아니라 노드였다

**첫 측정 — 워커가 모자랐다.** 50명이 초당 49건의 메시지를 15분간 보내는 부하를 걸었습니다. 메시지의 10%는 1차 키워드는 통과하지만 AI가 가려야 하는 문장으로 섞어, 검열 경로 전체가 일하게 했습니다. 워커는 곧바로 2개에서 상한인 5개까지 늘었지만, 다섯 개가 함께 처리한 양은 초당 27건이었습니다. 매초 22건씩 밀리면서 큐에 2만 건이 쌓였고, 검열 반영은 12분 넘게 늦어졌습니다.

모델이 느린 것은 아니었습니다. 추론 시간은 p95 0.42초로 정상이었고, 일꾼 수가 유입을 못 따라가 줄이 길어진 것이었습니다. 워커 하나가 초당 5.4건을 처리하니 상한을 10으로 올리면 초당 54건으로 유입을 넘어서야 했습니다. 상한 하나만 바꾸고 같은 부하로 다시 쟀습니다.

**두 번째 측정 — 늘렸는데 그대로였다.** 워커는 10개까지 떴는데 처리량은 오히려 초당 22\~25건으로 줄었습니다. 워커 하나당 처리량은 반토막이 났고, 추론 시간은 0.7초로 늘었습니다. 일꾼을 두 배로 늘렸는데 총량이 그대로라는 것은 워커들이 한정된 자원을 나눠 쓰고 있다는 신호였습니다. 노드 CPU를 보니 3대 모두 97\~99%였습니다. 워커는 10개가 됐지만, 그 워커들을 담은 노드의 코어는 그대로였던 것입니다.

**세 번째 측정 — 노드만 늘렸다.** 노드 수는 계산으로 정했습니다. 워커 10개가 각자 코어 하나씩을 쓰려면 2코어 노드가 5대 필요합니다. 워커 상한도 함께 올리면 결과가 무엇 때문인지 가릴 수 없으므로, 노드만 3대에서 5대로 늘리고 같은 부하로 재측정했습니다.

|               | 워커 5 · 노드 3 | 워커 10 · 노드 3 | **워커 10 · 노드 5** |
| ------------- | --------------- | ---------------- | -------------------- |
| 총 처리량     | 27 ops/s        | 22\~25 ops/s     | **43 ops/s (+72%)**  |
| 파드당 처리량 | 5.4/s           | 2.3/s            | **4.3/s**            |
| 모델 추론 p95 | 420 ms          | 700 ms           | **450 ms**           |
| 큐 피크       | 20,000          | 20,000           | **9,600**            |

처리량이 72% 올랐고 추론 시간도 회복됐습니다. 진단이 맞았던 것입니다. 다만 43은 여전히 유입 49보다 작아 큐는 쌓였고, 노드 5대도 CPU가 93\~97%로 다시 포화했습니다. 워커 외에 Chat Server가 초당 900건 가까운 메시지를 방마다 뿌리는 데 CPU를 쓰고 있어, 워커가 실제로 쥔 코어는 파드당 0.9개 정도였습니다.

![노드 5대의 CPU가 모두 포화된 모습](https://raw.githubusercontent.com/CLD-05/team1-chatguard-context/main/load-test/captures/e6-node-cpu.png)

_노드를 5대로 늘린 뒤의 노드별 CPU 사용률. 부하가 걸리자마자 다섯 대 모두 93\~97%에 붙는다._

세 측정에서 워커 파드 하나가 실제로 쓴 CPU는 각각 약 1코어, 0.55코어, 0.9코어였습니다. 두 번째 측정에서는 노드 3대의 코어 6개를 워커 10개와 다른 파드들이 나눠 쓰느라 하나당 몫이 절반으로 줄었던 것입니다. 파드당 처리량(5.4 / 2.3 / 4.3건)을 이 값으로 나누면, 파드 수와 노드 수가 달랐는데도 코어 하나당 초당 4\~5건으로 비슷했습니다. 코어당 처리 능력은 일정했고, 달라진 것은 워커 전체가 쥘 수 있는 코어 총량뿐이었습니다.

> **처리량 ≈ 워커가 실제로 확보한 코어 총량 × 코어당 약 4\~5 msg/s**

"워커를 몇 개 띄울까"가 아니라 "워커가 코어를 몇 개 쥐는가"가 처리량을 결정하고, **파드 오토스케일은 노드에 남는 코어가 있을 때만 효과가 있습니다.** 이 관계를 거꾸로 쓰면 목표 처리량에 필요한 노드 수가 나옵니다. 예를 들어 처음의 초당 49건을 소화하려면 워커용 코어가 10\~12개 필요하고, 다른 파드 몫까지 더하면 2코어 노드 6\~7대가 됩니다. 실측이 아니라 이 모델로 계산한 값입니다.

### 용량 이내에서는 목표를 충족한다

노드를 늘린 뒤에도 유입(초당 49건)이 용량(43건)보다 많았으니 검열 목표는 여전히 실패였습니다. 앞의 세 측정은 모두 일부러 과부하를 건 것이라, 이 시스템이 목표를 지키는 모습은 아직 한 번도 확인하지 못한 상태였습니다. 그래서 부하를 용량 안쪽인 초당 39건으로 낮춰 15분간 재측정했습니다.

| 지표                 | 목표     | 실측                     |
| -------------------- | -------- | ------------------------ |
| 검열 반영 지연 p95   | < 5 s    | **< 1 s** (확장 완료 후) |
| 메시지 전송 지연 p95 | < 300 ms | **40 ms**                |
| 전송 성공률          | ≥ 99.9%  | **100%**                 |

검열 지연이 목표를 넘은 구간이 한 번 있었습니다. 부하 시작 직후 약 1분 동안 p95가 **9.5초**까지 올라갔는데, 워커가 최소 2개에서 출발해 10개로 늘어나는 사이 큐가 300건 가까이 쌓인 구간입니다. 표의 "1초 미만"은 확장이 끝난 뒤의 값입니다.

![큐 깊이, 워커 수, 검열 반영 지연](docs/e7-moderation-autoscale.png)

_위에서부터 큐 깊이, 워커 수, 검열 반영 지연. 세 그래프는 같은 시간축이다. 시작 직후 큐가 차오르자 워커가 10개로 늘고 지연이 1초 아래로 내려온다. 14:40 무렵에는 워커가 4개까지 줄었다가 큐가 다시 쌓이자 10개로 돌아가고, 지연이 잠깐 4초대로 오른다._

같은 실험에서 축소와 재확장도 한 사이클 관측됐습니다. 큐가 비자 워커는 3분을 지켜본 뒤 1분에 하나씩 10 → 4까지 줄었고, 4개로는 유입을 따라가지 못해 큐가 100건 가까이 다시 쌓이자 곧바로 10으로 돌아갔습니다. 그사이 지연이 4초대까지 올랐다가 목표 안에서 회복됐습니다.

이 출렁임은 큐 길이를 신호로 쓰는 방식의 성질이기도 합니다. 워커가 유입을 딱 맞게 처리하고 있으면 큐는 0 근처에 머무는데, 스케일러는 이것을 "워커가 남는다"로 읽습니다. 그래서 모자라는 지점까지 줄였다가 다시 늘리게 됩니다. 이번에는 재확장이 빨라 목표 안에서 끝났지만, 최소 워커 수를 올리거나 유입 속도를 함께 신호로 쓰면 이 폭을 줄일 수 있습니다.

**메시지 유실 0** — 이 15분 동안 보낸 쪽(k6), 저장한 쪽(DB), 검열한 쪽(검열 로그)이 각자 센 건수를 대조했습니다. **36,215 / 36,214 / 36,214**. 저장된 메시지는 하나도 빠짐없이 AI 검열을 거쳤고, 차이 1건은 부하가 끝나는 순간 연결이 닫히며 마지막 메시지가 서버에 닿지 못한 경계 사건입니다.

### 천장을 넘기면 거절하고 느려질 뿐, 무너지지 않았다

**접속 천장 초과** — Chat Server는 파드당 연결 200개를 상한으로 두고 최대 5파드까지 늘어나므로, 설계상 천장은 1,000 연결입니다. 1,100명으로 이를 넘기자 접속 수는 정확히 1,000에서 멈췄습니다. 자리가 없는 약 100명은 "잠시 후 재시도" 신호로 거절된 뒤 잠깐 기다렸다 다시 시도하기를 반복했고, 누가 나가 자리가 나면 그때 들어갔습니다. 거절 11,418건은 이 순환이 쌓인 횟수입니다. 그동안 서버 재시작은 0회, 이미 입장한 사용자의 전송 지연은 40\~55ms를 유지했고, 영구적으로 실패한 클라이언트는 없었습니다.

![파드별 연결 수가 상한에서 그리는 수평선](https://raw.githubusercontent.com/CLD-05/team1-chatguard-context/main/load-test/captures/e8-per-pod-connections.png)

_파드마다 상한 200에서 수평선을 그린다. 넘긴 요청은 거절되고 재시도로 흡수됐다._

만석인 파드의 메모리도 이때 측정할 수 있었습니다. 연결 200개를 문 파드가 한도(1Gi)의 45%만 써서(연결당 약 150KB), 잠정값이던 상한 200이 메모리 기준으로 안전하다는 근거가 생겼습니다. 메모리만 보면 연결 상한을 올릴 여지가 있지만, CPU와 메시지 전파 부하는 따로 따져야 해서 200을 유지했습니다.

**큐 적체 경보** — 접속 천장 실험은 접속 축 실험이었지만 각 사용자가 메시지도 보내 초당 41건의 검열 부하가 함께 걸렸고, 큐가 1만 건 넘게 쌓였습니다. 검열 큐 적체 경보(`ModerationQueueBacklog`)는 큐가 50건을 넘은 상태가 5분 이어질 때 울리도록 걸어뒀는데, 오토스케일이 최대치에 닿고도 큐를 줄이지 못하는 상황을 사람에게 알리기 위한 기준입니다. 이 실험에서 경보가 실제로 발화해 Slack으로 알림이 왔고, 부하가 끝나 워커가 쌓인 큐를 비우자 10분 뒤 해소 알림까지 왔습니다. 알람을 걸어두기만 한 것이 아니라, 발화부터 해소까지 사람에게 도달하는 경로 전체를 실제 장애 상황에서 확인한 셈입니다.

**극한 과부하** — 마지막으로 실측 용량의 약 11배(초당 485건)를 15분간 걸었습니다. 어디가 먼저 막히는지 보려는 실험이라 목표 달성 여부는 따지지 않았습니다. 파드 재시작과 오류는 0이었고, 포화된 자원은 이번에도 노드 CPU 하나였습니다(DB 커넥션 60/85, Redis CPU 8.9%). 다만 무너지지 않은 대신 느려졌습니다. 같은 시간 로그인 응답은 p95 10.7초까지 늘었고, 보낸 메시지의 약 20%는 60초 세션이 끝나기 전까지 발신자에게 돌아오지 못했습니다(평소 1% 미만). 워커와 Chat Server가 같은 노드에서 CPU를 나눠 쓰는데 워커에는 CPU 상한이 없어서, 노드가 포화되자 Chat Server도 함께 느려졌습니다. 여기에 Chat Server의 DB 커넥션 풀까지 바닥나 요청이 줄을 섰습니다([한계와 다음 단계](#한계와-다음-단계)). 과부하에서 프로세스가 죽는 대신 처리가 늦어지는 쪽으로 버틴 셈입니다.

### 장애 주입: 진짜 원인은 Redis가 아니었다

개발 중에 Redis primary가 교체되자 Chat Server 파드 3개가 한꺼번에 재시작된 일이 있었습니다. 우연인지 구조적인 문제인지 가리려고, ElastiCache의 failover 테스트 기능(`aws elasticache test-failover`)으로 부하 없이 같은 장애를 일부러 일으켰습니다. Redis는 2노드 자동 failover 구성이라 복제본 승격은 정상이었지만, 그 사이 **Chat Server 3파드가 또 전원 재시작**됐습니다.

로그를 따라가니 원인은 Redis가 아니었습니다.

1. primary가 교체됐는데 Redis 클라이언트가 DNS 캐시 때문에 죽은 옛 주소로 계속 재접속을 시도
2. 그동안 앱의 헬스체크 응답이 최대 40초간 지연 (Redis 상태 확인에서 대기)
3. Kubernetes의 liveness 프로브가 이 헬스체크를 1초 타임아웃으로 검사 → 3회 실패 → **"앱이 죽었다"고 판단하고 재시작**
4. 그런데 Redis 클라이언트는 **44초 만에 스스로 재접속에 성공**

즉 몇 초만 더 기다렸으면 살았을 파드를 프로브가 먼저 죽인 것입니다. 같은 장애를 겪은 워커는 재시작이 0이었는데, 워커의 프로브는 의존성을 보지 않는 단순 생존 체크였기 때문입니다. 이 대비가 원인을 확정해줬습니다.

**조치** — liveness는 프로세스 생존만 보는 경량 엔드포인트로 분리하고, 의존성 상태는 readiness에만 반영했습니다. Redis 응답 대기는 3초로 제한하고, 프로브 타임아웃도 앱의 응답 상한에 맞춰 조정했습니다. 그리고 같은 장애를 다시 주입했습니다.

|                    | 조치 전    | 조치 후 |
| ------------------ | ---------- | ------- |
| Chat Server 재시작 | 3파드 전원 | **0회** |
| Redis 재접속까지   | 약 44초    | 약 40초 |

| 조치 전 — 3파드 동시 재시작                                                                                              | 조치 후 — 평평한 0                                                                                                       |
| ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| ![before](https://raw.githubusercontent.com/CLD-05/team1-chatguard-context/main/load-test/captures/e5-restarts-step.png) | ![after](https://raw.githubusercontent.com/CLD-05/team1-chatguard-context/main/load-test/captures/e5p-restarts-flat.png) |

재접속에 걸린 시간은 거의 같습니다. 이 조치는 **복구를 빠르게 한 것이 아니라, 복구를 기다리는 동안 죽지 않게 한 것**입니다. 파드는 그 40초 동안 트래픽에서만 잠시 빠졌다가 돌아왔습니다.

**다른 종류의 장애에서도 같은가.** 파드가 올라가 있는 노드 하나를 예고 없이 정지시켰습니다(`aws ec2 stop-instances`). 그 노드 위의 Chat Server와 워커는 20\~30초 안에 다른 노드에서 다시 떴고, 노드 그룹이 약 3분 만에 새 노드를 채워 넣었습니다. 나머지 노드의 파드는 한 번도 재시작되지 않았습니다. 알람도 1\~2분 안에 이 장애를 감지했지만, 발화 기준(10분 이상 지속)에 닿기 전에 복구가 끝나 사람을 부르지 않았습니다.

![노드 정지 직후 대기 상태 알람의 증감](docs/az-kill-alerts-pending.png)

_노드 정지 직후 발화 대기(pending) 알람이 13건까지 쌓였다가 복구와 함께 줄어든다. 발화(firing)에 이른 알람은 0건. 마지막까지 남은 2건은 이 장애와 무관한, EKS 환경의 알려진 오탐이다._

앞의 큐 적체 경보가 울린 것과 함께 보면, 사람이 필요한 지속 장애에만 울린다는 설계가 양쪽 모두 실측으로 확인된 셈입니다.

## 담당 범위

## 한계와 다음 단계

**측정된 범위** — 실측 처리량은 초당 40여 건 수준으로, 실제 라이브 스트리밍 서비스의 규모와는 거리가 있습니다. DB와 Redis가 "여유"였다는 판정 역시 측정한 부하 범위 내에서의 결론입니다.

**노드 자동 확장** — 부하 테스트의 결론은 파드 오토스케일이 노드 용량 안에서만 유효하다는 것이었는데, prod 노드 수는 5대로 고정돼 있고 3→5 증설도 Terraform 값을 직접 바꿔서 했습니다. 다음 단계는 노드 자체를 자동으로 늘리는 것(Cluster Autoscaler나 Karpenter)입니다. 다만 노드 급사 실험에서 대체 노드가 준비되기까지 약 3분이 걸렸으므로, 노드가 뜨는 동안은 기존 노드의 여유로 버텨야 합니다. 노드 종류도 바꿀 여지가 있습니다. 포화된 자원은 CPU뿐이었고 메모리는 극한 부하에서도 노드당 1/3만 썼으므로, CPU는 같고 메모리가 절반인 인스턴스로 바꾸면 같은 비용으로 더 많은 코어를 확보할 수 있습니다.

**DB 커넥션 풀** — 극한 과부하에서 DB 커넥션은 85개 중 60개로 여유였지만, Chat Server 쪽 커넥션 풀은 이미 바닥나 있었습니다. 커넥션을 기다리는 요청이 최대 300개까지 쌓였습니다. 오류나 타임아웃은 없었지만, 이 대기가 앞서 본 응답 지연으로 이어졌습니다. 부하가 더 커지면 DB보다 이 풀이 먼저 한계가 됩니다. 풀을 키우면 대기는 줄지만 DB 커넥션 상한에 그만큼 빨리 닿습니다. 지금은 Chat Server 파드가 풀 기본값대로 10개, 워커 파드가 1개씩을 쓰므로(실측 60 = 5 × 10 + 10 × 1), Chat Server 상한을 8로만 올려도 85를 넘습니다. 풀 크기를 명시적으로 정하는 것과 Chat Server 상한을 올리는 것은 함께 결정해야 합니다.

**미적용 항목** — TLS 미구성(도메인·인증서 미할당), Slack 알림은 prod에만 연결. Chat Server가 줄어들 때 연결된 사용자에게 "곧 닫는다"를 먼저 보내고 클라이언트가 다른 파드로 재접속하는 경로는 서버와 클라이언트 양쪽에 구현했지만, 실제 축소 상황에서 실측하지는 않았습니다.
